§2  The finding: two bases under one set of module names
------------------------------------------------------------------------------------------

Lean loads one olean per module name (first hit on LEAN_PATH) and does not re-check an
imported olean against the oleans its dependents were compiled with.  A joint module whose
import closure takes module X from one side while a dependent of X was compiled against the
other side's X is incoherent, even if it elaborates.  The check used here
(build-integration/closure.py + coherence.py): resolve the closure under the joint path and
under each side's compile-time path, and require identical olean bytes for every module that
is not rebuilt in the joint directory.

Measured:
* R1Z.Sem1UniformR1 (privacy, 304 user modules) against ExtractedQM31SamplerCorrect (spend,
  pinned journal correct-c): 28 shared user module names, 23 with different oleans.  Six differ
  in SOURCE: AspisFormal.CircleGroupOrder (privacy pinned-v7 `import Mathlib`; spend 70b2727f
  narrowed imports), FS.LemmaA and FS.Theorem (spend adds Mathlib.Tactic.Linarith /
  Mathlib.Logic.Equiv.Fin.Basic), R0C.ModuloCounting and R0C.ModuloField (spend adds explicit
  imports incl. AspisFormal.CircleGroupOrder), WideTower (spend imports AspisV8R15.ExactTower*
  instead of AspisFormal.V5ComponentCQM31TowerExact).  The other 17 (FS.Statement, R0C.Counting,
  thirteen AspisV8R19.*, ...) have identical sources and differ only because they were rebuilt
  on the narrowed base.
* R1Z.BatchedAlgebra with the mirror replaced by the spend-path originals (R1FoldCoefficientBridge
  etc. from aspis-r1-concrete-decoder-20261013/objects), plus its three dependents: closure 260
  user modules, 108 conflicts (Wide.*, R0P.*, R0C.*, R0FS.*, FS2.*: the opening-layer objects
  were compiled on that workspace's rebuilt copies).  Rebuilding the privacy side on the spend
  base would need 100 modules recompiled (44 Wide, 19 R0Z, 12 R0P, 10 FS2, ...).
* The spend side is itself a forest of per-target coherent overlays, not one base:
  AspisFormal.CircleGroupOrder is 070c1d46.. in the sampler overlay and 05c7d259.. in the G3
  union; privacy has 39ea3fa6...

So "replace R1Mirror by direct imports" cannot mean "load the spend path's existing oleans
next to the privacy oleans": the bases differ under the same names.  The single build must
compile every module once, from one source per module name, on one base.

§3  Target single build
------------------------------------------------------------------------------------------

Workspace.  A new host workspace J = /home/dombarker/project-offloads/aspis-joint-<date> with

Sources.  J/sources is generated from ONE repo revision by a manifest script (to be written,
build-integration/joint-manifest.py): spend-path docs/research/100bit-spend-path-20261013/lean

sources for one name (the six of §2, and any found later), the spend version is selected:
the differences found are import narrowing, the spend path is frozen, and narrowing lowers
the import baseline.  Privacy files that relied on the wider imports get explicit imports
(privacy-side edits only, each listed in the manifest).  The manifest has a --check mode
(AGENTS.md preflight): every module name has exactly one source; every import resolves inside
the manifest or to Mathlib/Aeneas/Lean; no R1Mirror.* module is present.

Roots and namespaces.  Module roots: the spend release roots (as listed by the spend path's
accepted targets), R1Z.PrivacyR1P / R1Z.PrivacyGamesSamplerR1 / R0Z.BuilderWitnessMerged on

R0Z.*, R1Z.*); the one known clash, AspisR1.childIndex vs AspisV5ComponentCConcreteFoldLinearity
.childIndex, is two different constants bridged by rfl (BatchedAlgebra.childIndex_bridge).
Duplicate declarations, if any, show up as import errors at R1J.Integration.

    The closure needs the spend-path files NaturalProjection, RoundPairing, FirstFold and

    nine patched files: Data/Array, Data/Vector, ReduceZMod, BvTac, Step, StepArraySpec,

    Scalar, Array, RustAttributes all differ.  Two Aeneas trees cannot be on one LEAN_PATH.

(c) SemRows01 / QM31SamplerLaw.  QM31SamplerLaw is a property of s1 alone and follows from
    the spend sampler: s1 := ι ∘ decode ∘ toCurrent ∘ (the sampler output of
    ExtractedQM31SamplerCorrect.sample_total) ∘ toArr, with toArr : (Fin 32 → UInt8) ≃
    Array U8 32#usize and ι : QM31Exact → K injective (the QM31 ↔ K transport; a ring
    embedding in use).  rank := SourceSamplerByteRank.rank ∘ toArr as an Equiv onto
    Fin 2^256; emb n := ι (decode (toCurrent (digits of n))) with injectivity below p⁴ from
    the digit canonicality and decode injectivity (decode_eq_iff content); sample from
    sample_total + qm31Digits depending only on x mod p⁴.  Statement surface: a
    statement-only interface module R1Z.SamplerLawIface (Mathlib-only closure, so its olean
    is valid on both bases) holding the four fields; Sem1UniformR1.QM31SamplerLaw is built
    from it field by field.  SemRows01 is NOT a consequence of the sampler theorems: it says
    the wire's decoder W.dec reads χ = sem 1 from row 1 by s1 and λ = sem 0 not from row 1.
    It needs the concrete R1Wire (W.dec from the spend path's semantic decoder) and belongs
    with (d).
(d) Rspend/Wspend.  Rspend (SpendRelation.lean:41) and Wspend map to RustWitness/RustPublic/
    ModelWitness (DESIGN-BUILDER-MODEL §12.6), following glue.rs `records`; Rspend⁺ :=
    Rspend ∧ (transfer → change[7] ≠ 0) (D50).  The map is a joint-root definition in
    R1J.Integration with PubCorr and WitnessOk as theorems from Rspend⁺'s range facts.  It
    needs SpendRelation (spend) and BuilderWitnessMerged (privacy, Aeneas) in one closure:
    after (f) and (b).
(e) line_identity.  R1Z/BatchedAlgebra.line_identity / line_layer_identity give, for every
    message m and α₁, line fold of the four stored children = second encoder of the
    α₁-folded message.  On the soundness side this is the honest-data form of match1
    (MatchingSupport: curveValue (channels V) α₁ (parentIndex i) = secondEncoder f
    (parentIndex i)).  The exact consumer premise (cited in the merge note as
    R1QueryResidualBridge) is to be named by the soundness lead; the bridge lemma lives in
    R1J.Integration once BatchedAlgebra and R1QueryResidualBridge share the base (after f).
    The R1Mirror replacement (a) is what makes the constants identical: both sides then
    talk about the same AspisR1.* declarations.

------------------------------------------------------------------------------------------

* Privacy modules peak 6.65-6.95 GB under -M7000 / MemoryMax 7G (this job: Batched 6.95 GB,
  VerifierRelationsR1 6.80, RfLine 6.75, BatchedAlgebra 6.71, FirstFold 6.69 on the privacy
  base).  The peak is almost all import baseline: 29 modules in the privacy closure
  `import Mathlib` whole (24 AspisFormal ones, incl. the pinned-v7 CircleGroupOrder that most
  of the tree imports, and R0P.MessageDescent, R0Z.GoodDensity, R0Z.HermiteSpan,
  R0Z.KernelImage, R0Z.StatisticalDistance).  The same spend-path-sampler-base compile of
  SamplerLawSpend peaked at 3.85 GB.  In J the narrowed spend base lowers the baseline only
  where no closure module still imports all of Mathlib; step 2 lists them, and narrowing the
  five privacy ones is a privacy-side edit.  Until then any privacy module that adds real
  elaboration work over the baseline is at risk of the 7 GB cap (BatchedAlgebra 3627 failed
  at 7.17 GB in D33).  Caps are not raised; a module that crosses is split or its imports
  narrowed (AGENTS.md resource rule 5).
* Four slots × 7 GiB = 28 GiB, inside the run2 reservation check (55 GiB populated cap).
* No `lake build` of the cold tree (resource rule 1): per-module compile only.
* Aeneas-importing privacy modules (step 5) and the Poseidon/certificate modules have the
  largest proof terms; they are compiled one at a time with the slot count reduced if two
  such modules would overlap.
* Pre-existing hazard found by the closure tool in the privacy workspace: six mtime
  inversions (e.g. R0P.CoreExt is 53,306 s newer than its dependent R0P.Copy).  objects2 has
  dependents compiled before a later recompile of their dependency; J's single topological
  build removes this class of hazard.
