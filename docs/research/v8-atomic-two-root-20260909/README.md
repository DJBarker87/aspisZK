**Atomic two-application-root experiment — 9 September 2026**

Milestone I is demonstrated in complete signed TxV1 transactions in LiteSVM using the retained real V8 verifier: one Aspis private transfer and an authenticated, deterministic depth-20 destination inbox insertion commit together under separate program owners. The handoff is **message only**. Only the Aspis transition is ZK-proved. The largest successful tested transaction consumed **1,070,707 of 1,200,000 CU**, an increment of **42,161 CU** over its identical-proof single-root control. Its signed wire is **3,236 bytes** and the proof body remains **40,282 bytes**, with zero proof-byte increase.

This is an inactive research implementation, not a replacement for ongoing V8 security work. Proof storage was preloaded as a sealed synthetic account. The demonstrated object is the atomic verification-and-settlement transaction, not the complete upload lifecycle. No network transaction, deployment, witness upload, real funds, push or merge was performed.

**What executes.** A is the actual selected output-lane application root, identified independently by Pool master and lane; B is the separately owned SHA-256 inbox PDA. A's master/checkpoint still authenticate historical forest membership. A consumes its globally scoped source nullifier and appends its ordinary recipient/change pair. B appends a receipt H binding that same ASQ8 payload, source context and destination context. Its receipt creates no spendable asset. The fixture's 1,000 = 600 + 400 value remains conserved within A; calling the B copy a value transfer would be incorrect.

The original design attempted a B-to-Pool CPI and failed with Pool's intentional `0x41532036` top-level-only guard. The retained design instead uses B precheck, original top-level Pool ASQ8, and B final insertion as three instructions in one transaction. The instructions sysvar authenticates their exact order, bytes and privileges. Pool keeps its authenticated `ASQ8 → ASF8 → verifier → ASR8` path. B checks the canonical Pool marker and live new lane state after the successful source instruction. A later error rolls back both owners' changes. No cross-instruction caller-supplied verification receipt, weakened Pool guard, generic coordinator, VM or external integration is introduced.
