# R425 unit-constant frontier: pinned translator inventory

This is a read-only source/API inventory for the R424 translation failure at `InterpExpressions.ml:574` on the constant displayed as `()`, in the `Iterator::try_fold` definition (Rust source span 2486:4–2490:35). Agent r241 separately records the immutable R419 LLBC row and its exact constant JSON, so this note does not duplicate that row.

## Findings

Charon represents the unit constant as `CAdt (None, [])` with `mk_unit_ty` (`charon-ml/src/ExpressionsUtils.ml:19`). Its formatter treats tuple aggregates separately: `TTuple` is printed as parenthesized fields (`PrintFmt.ml:477–484`), so the empty tuple/unit prints as `()`. The Charon `matches.rs` UI fixture contains `let () = ();`; its checked-in `.out` includes `_0 = ()` (source/output hashes listed below). This confirms the Rust frontend fixture exercises a unit rvalue in MIR output. It does not establish that Aeneas accepts that constant.

In Aeneas, call operands are evaluated before the call (`interp/InterpStatements.ml:432–433`, `eval_operands`). `interp/InterpExpressions.ml:399ff` handles a `Constant` by matching its `constant_expr_kind`. It has cases for `CLiteral`, `CTraitConst`, `CVar`, `CFnDef`, `CRawMemory`, and `COpaque`; the final wildcard at lines 573–575 raises `Found unexpected constant: ...`. There is no `CAdt` arm in this evaluator. Therefore the observed `CAdt(None,[])` unit constant reaches the exact rejecting fallback. This reports the current behavior only; this inventory does not propose or implement a lowering.

`PrePasses.apply_passes` first runs the crate-wide `update_array_default` and `add_pending_return_carrier`, then the listed function passes (`PrePasses.ml:3597ff`). The individual function-pass list includes closure lifetime repair, region erasure, metadata-only raw-pointer elimination, unreachable removal, nested return/loop transforms, borrow/storage cleanup, panic simplification, global-access decomposition, and statement-ID refresh. No listed pass is an explicit CAdt/unit normalization. `Main.ml:734ff` applies these passes before either unit-function testing or `Translate.translate_crate`. A bounded source search found no direct `CAdt` case in `PrePasses.ml`, `interp/InterpExpressions.ml`, `llbc/ValuesUtils.ml`, or `llbc/Contexts.ml`; this is not a claim about all possible generic visitor effects.

Tuple support exists for already-evaluated values and types, not as a unit-constant evaluator arm: `ctx_adt_get_instantiated_field_types` handles `TTuple` by requiring no variant and no region arguments and returning tuple generic types (`llbc/Contexts.ml:648–672`); `mk_etuple` constructs runtime `EAdt` tuple values (`llbc/ValuesUtils.ml:53–60`). These are distinct code paths from `Constant { kind = CAdt ... }` evaluation.

The separate `SymbolicToPureTypes.translate_constant_expr_kind` handles only `CGlobal`, `CVar`, and `CLiteral`, then raises “Unsupported constant expression kind” (`symbolic/SymbolicToPureTypes.ml:28–33`). That is the const-generic translation path, not the function-operand evaluator that produced this failure.

The Charon tests searched include general unit MIR cases (`matches.rs/.out`, `rvalues.rs/.out`) and a large iterator fixture (`iterator.rs/.out`). The iterator test output contains many `try_fold` declarations but no discovered `any()`-specific unit-constant test. No sourcechecker test proving Aeneas accepts this exact CAdt unit operand was found in the bounded search.

The immutable LLBC row collected by r241 is useful for the phase question: the same structural constant (`kind = Adt [null, []]`) occurs at the same function-58 `Ref.ptr_metadata` path in both R396 input SHA `399020435e94aaa7135c06d68445e9b936bd22fe6d1e1d197ee708d448d584ae` and R419 candidate SHA `7f82eaabe855e89d735b21f9af5f6a983abea6b2f4d93d4b8bae747abd2829e2`. The type's hash-cons ID differs (R396 594, R419 19), but both decode as the empty tuple. Thus this constant predates the R419 projection rewrite; the rewrite did not create it. The exact occurrence receipts are preserved at `../llbc/R396-unit-constant.json` and `../llbc/R419-unit-constant.json`.

The Charon AST documentation (`Generated_Types.ml:354–386`, SHA `6e977831c8fb7a3e1b6b77e1b98e5cc71de8841186f98c5de5fd68c93fdb9794`; mirrored in `charon/src/ast/expressions.rs:608–630`, SHA `7339c83c73fc0d3399d1da03aaae7f6190a9bc6bbfc8d6c6657e4a0690b6e3b5`) says CAdt constants are eliminated by the `regularize_constant_adts.rs` micro-pass. That named Rust pass source is absent from the pinned Charon source checkout inspected here, so its implementation and ordering cannot be independently verified from this snapshot. Its advertised existence does not explain this nested `Ref.ptr_metadata` occurrence: the captured R396 and R419 LLBC still contain it. The Aeneas R385 pass ordering starts after Charon has emitted LLBC, and none of its listed Aeneas prepasses names CAdt normalization.
