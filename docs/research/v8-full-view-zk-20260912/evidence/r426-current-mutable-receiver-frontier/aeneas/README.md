## MIR CopyForDeref and call-argument representation

The locally pinned Rust compiler source is nightly `1.98.0-nightly`, commit `14210df0e27ccd7d9e6a05b8085cbd438e4bbc65`, from `/home/dombarker/.rustup/toolchains/nightly-2026-06-01-x86_64-unknown-linux-gnu/lib/rustlib/rustc-src/rust/compiler`. Its `Rvalue::CopyForDeref` documentation says the rvalue is a read that drop elaboration treats specially, guaranteed by the `Derefer` MIR optimization to feed a `DerefTemp`; it is disallowed in runtime MIR and replaced by normal copies (`rustc_middle/src/mir/syntax.rs:1455–1465`, SHA256 `dd77a1dddc833bf073bec4b35274d5f519819f2e309f48411371e2e9cd376679`). `rustc_mir_transform/src/erase_deref_temps.rs` says explicitly that it does not want a retag because the assignment may copy a mutable reference “we can't actually copy”; it rewrites `CopyForDeref(place)` to `Use(Copy(place), WithRetag::No)` (lines 17–22, SHA256 `1a163cf0e065a60ba1f2696d4cfb62a5da60e95be1cca9782df57cd2868e1e1a`). Runtime-lowering places `EraseDerefTemps` after drop elaboration and before box-deref elaboration (`rustc_mir_transform/src/lib.rs:625–649`).

The same MIR docs caution that `Call` semantics need clarification; they say arguments are owned by the callee, while `Operand::Copy` is a place load (Copy-type restriction before drop elaboration, no such requirement after) and `Move` has special call in-place behavior (syntax.rs:790–821, 1303–1327). In this build’s Charon translator, `translate_function_call` calls `translate_arguments`; the argument loop simply applies `translate_operand` in order, and `translate_operand` preserves `mir::Operand::Copy` / `Move` as corresponding LLBC variants. Charon's `WithRetag` is attached to `Rvalue::Use` and described as a Rust aliasing-model flag; it is not an extra marker on call arguments. The exact relevant sources and excerpted lines are in `charon-excerpts.txt`.

This establishes a pinned compiler path that intentionally exposes a non-copying mutable-reference `Copy` representation after MIR lowering, alongside a Charon path that serializes it as LLBC `Copy`. It does not by itself establish that the R419 `Iterator::next` argument arose from this exact `CopyForDeref` path; r241's exact LLBC/source census is needed to identify that occurrence. It also does not establish the appropriate Aeneas runtime treatment. In particular, no `Copy`→`Move` rewrite is proposed here: the source location may be used again, so any reborrow modeling must account for its lifetime and later uses.
