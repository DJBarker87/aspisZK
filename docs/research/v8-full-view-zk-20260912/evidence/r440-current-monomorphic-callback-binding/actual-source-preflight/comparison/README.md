# R437 → R440 LLBC structural comparison

This is a read-only, lossless structural comparison of the pinned R437 output and the successful R440 actual-mono-closure output. It records generated AST/declaration differences only. It does not assert source execution equivalence, validate a semantic lowering, or close a proof/security obligation.

Inputs:

- R437: `.r21-scratch/r437-pointer-source-boundary/root-launch-a/saved-output/R437PointerWrapperLayout.llbc`, SHA-256 `bafe9c1297a8ea92eaea3c37c685da3f5d3fe2e04c335ac9f1f4d64c4312386c`.
- R440: `.r21-scratch/r440-mono-closure-binding/actual-source-preflight/lead-launch-a/saved-output/R440ActualMonoClosure.llbc`, SHA-256 `01cd5ddc7086bba5f4e92802f90e59cce4034cf519d495ec35f925b91a6f033d`.

Both reports have `has_errors=false`; their saved Charon receipts show exit 0 and zero swap. The comparison script expands only Charon `HashConsedValue` and `Deduplicated` wrappers, with collision, missing-reference, and cycle failures. The full expanded snapshots and the exhaustive literal diff are retained beside this README.

The 778 literal differences partition into 52 paths in function rows, 537 in the `short_names` vector, 188 in `ordered_decls`, and one `translated.options.dest_file`. No other expanded path differs. The 52 function-row paths lie entirely inside the 16 source-inventoried Fn-family `Call.func` nodes. For each node, the original call names a TraitImpl/method slot and the candidate call names the unique method function identified by the corresponding `FunDecl.src` owner. The candidate generic arguments in every namespace (regions, types, const generics, trait refs) equal the exact original impl arguments followed by the original method-call arguments. No region was dropped or normalized. The call's other fields, including operands, destination and unwind, are exact. Replacing only these 16 `func` subtrees makes all function rows equal.

The other declaration tables compare exactly after strict hashcons expansion: 76 type rows, 50 globals, 16 trait declarations, and 68 trait implementations. This includes trait methods and destructor data. All function-table IDs and null slots remain at the same indices. Source rows, signatures, item metadata, spans, files, and translated options compare exactly except the separately identified output path. `short_names` has the same exact key/value map; only its vector ordering differs.

The native `ordered_decls` contents differ in membership and order, so the audit does not treat them as a reorder-only change. Both outputs encode 100% of listed groups as `NonRec`; no `Rec` group appears. R437 has 264 ordered items (Fun 150, Type 70, Global 21, TraitImpl 16, TraitDecl 7). R440 has 262 (Fun 153, Type 70, Global 21, TraitImpl 11, TraitDecl 7). The added items are Fun71 (`challenge_secure_circle_point` call_once), Fun93 (`sample` call_once), and Fun141 (`r24_canonical_mul` call). The removed items are TraitImpl16, 31, 53, 54, and 55 under those same method families; impl53 is not one of the 16 direct old call targets. All listed IDs are valid and unique. The 15 changed callsites whose callers are themselves in the candidate ordered list have their direct target function before the caller. Fun139’s changed callsite points from impl54/method0 to source-owned Fun140, but neither Fun139 nor Fun140 is in either ordered list.

The pinned `DepsForItem` source copy used as ordering context is `../..` relative to the worktree at `.r21-scratch/r288-private-batch-ordering/pinned-reorder_decls.rs`, SHA-256 `8a1176e29a51a83c82ff5a7df2aa11021e3e0c254e9fd6c656c0a92314ba2632`. This comparison did not reconstruct the complete typed dependency graph or independently explain why the extra impl53 row leaves the listed closure. The full group lists and 188 literal ordered-declaration differences remain available in both expanded snapshots and `literal-expanded-diff.json`; group coverage is explicitly not equal.

The extractor command plans match on start root, includes, features, monomorphization, environment, frozen source hashes, and base-command SHA. Their argv differs in the observer executable and fresh output destination.
