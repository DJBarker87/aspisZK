# R440 saved-fixture comparison audit

This is an independent, read-only comparison of the saved baseline and successful candidate LLBC. It establishes serialized structural differences only; it makes no execution-semantics, theorem, or security claim.

The raw baseline is `../baseline-saved/baseline.llbc` (SHA-256 `331b2a1fdcbb21279a4e3f92d995bac93ffa05c78d847a3576a2f6e912e93445`) and the candidate is `../candidate-saved/baseline.llbc` (SHA-256 `6bb4254faef4498b51ebe7d97213a457da740391799562302501e9a701240eb7`). Both report `has_errors=false` and successful exit status. The audit compares the saved losslessly hashcons-expanded JSON snapshots from the sibling `comparison` directory, while retaining and hash-pinning both raw LLBC files. No LLBC field was normalized away except the explicitly listed comparison allowances below.

All expanded type, global, trait-declaration, and trait-implementation tables compare exactly, including trait method/destructor data. All five function declaration IDs remain in the same table order. Fun3, the callback body and signature, compares exactly. The only executable body differences are two `Call.func` pointers:

- Fun1 statement index 9 (statement ID 56): TraitImpl 1, method slot 0 becomes regular Fun3. The call's impl region arguments `[Body 23, Body 24, Body 25]` followed by method region argument `[Body 26]` are preserved in that order in the new pointer. Its args, destination, target, unwind, statement ID/span, and surrounding body fields are exact.
- Fun2 statement index 3 (statement ID 77): TraitImpl 1, method slot 0 becomes regular Fun3. Its impl region arguments `[Free 0, Free 1, Free 2]` followed by method region argument `[Body 11]` are preserved in that order. Its args, destination, target, unwind, statement ID/span, and surrounding body fields are exact.

For both call pointers, all four generic namespaces (regions, types, const generics, trait references) are checked as exact concatenations of the original impl and method arguments. No region is erased or canonicalized. All other serialized fields compare equal after removing only those two `Call.func` subtrees. The output `dest_file` differs because each run wrote into its own fresh output root. `short_names` has the same exact key/value contents; only vector order differs. `ordered_decls` has the same 14 nonrecursive groups and exact item-membership multiset, but a different order: Fun3 is placed before both Fun1 and Fun2 in the candidate. The final whole-tree check canonicalizes only that ordering for equality after separately checking every group's kind and membership, and verifies the candidate dependency order.

The baseline and candidate receipts use the same fixture source SHA-256 `86f696b86419a99bc2a9da74fb99b47694bca8d66f67c7bf6b6bf2d263075554`, pinned Charon revision `cb50ff16b9f1066b8a97dc06da704de2da2fa41c`, and wrapper SHA-256 `b2b0961a3c55aca64752b2fa4a4701ba0c06b860236979e5727c07de8ac2310c`. The candidate uses its intended changed driver; the baseline uses the original driver. Both have zero swap. This audit did not rerun either process.

`audit-v1-raw-table-check.py` and `audit-v2.py` preserve failed audit drafts. V1 compared raw hashcons-encoded rows directly, which is not a valid structural equality check across different hashcons numbering. V2 expanded the values but did not canonicalize ordered declaration groups for the final whole-object comparison; it therefore stopped at that assertion. `audit-v3.py` is the final passing checker. Its report is `audit.json`; `audit-v3.stdout.json` is the captured output. No source, toolchain, or LLBC artifact was edited.
