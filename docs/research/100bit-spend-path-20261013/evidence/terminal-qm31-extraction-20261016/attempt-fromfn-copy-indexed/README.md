# Isolated Copy-helper / indexed-loop extraction experiment

This bundle records one source-only extraction experiment, layered on the pinned F row-helper input snapshot. It is not an adopted verifier build, a Lean proof, or a source-equivalence result. It does not establish that the new local array helper is equivalent to Rust `core::array::from_fn`, or that this candidate matches unchanged production Rust.

The base snapshot is attempt F, source revision `39cda89cc9e06961684ec5fd0209312b5c15ec29`, with 133 source rows and merged-source manifest SHA-256 `cc3ca00c56efc58d34f3dbabee9fd52900d3d7b0e9f44675f2e493582b7d6a24`. The full candidate input is retained in `input/`, with the source manifest, `actual-merged-input.patch`, and `input-candidate.tar.gz`. The earlier `candidate.patch` is a source-kit draft with different crate-root framing; it is retained as such and is not the exact merged-input patch. The three changed base files and G comparison output are retained under `provenance/`. `verify_candidate.py` checks the 133-row source snapshot and confirms only the intended helper root file and two source files differ from F. The candidate manifest SHA-256 is `093863c9067dcc784cb28561cc96de5ef91f1e13328eb2f1b0063445638fd4d2`. Cargo manifests and lockfile remain unchanged from the candidate extraction scaffold; the lock SHA-256 is `e1ff38c257fe01c028da4dfecba548f9276ceb587d35e33decafa4b72f5dd359`.

The temporary candidate makes 18 `array_from_fn_copy` call-site substitutions. The helper initializes `[init; N]`, invokes the `FnMut` in increasing index order, and overwrites one cell per call. It also changes two reverse Horner loops in `composition_parts` from owning-array `into_iter().rev()` to `(0..array.len()).rev()` with indexing. This preserves the intended source-level order in the candidate, but compiler/runtime behavior and semantic equivalence have not been established. No production files were changed.

## Build and translation record

The run used Rust `nightly-2026-06-01` (`1.98.0-nightly`, commit `14210df0e27ccd7d9e6a05b8085cbd438e4bbc65`, LLVM 22.1.6), Charon 0.1.223 (binary SHA-256 `daad69bea1114042a2d2fbd3dfde99922b152d4f57023bf8edb83e5a6f336af8`), and Aeneas (binary SHA-256 `959659a6aafc6a6a975b4dc67ee9d779a269b988bd44b3b31a77cf023b1709e3`). Cargo ran offline, locked, release, one job, features `r0,pool-v1-kernel`, no default features, release opt-level 3, overflow checks enabled. The runner and exact per-stage commands are retained.

Build, Charon, and Aeneas each exited 0 in separate `MemoryHigh=4G`, `MemoryMax=6G`, `MemorySwapMax=0`, `TasksMax=128` scopes, with 300-second per-stage timeouts. Their wall times / process RSS / swap were: build 65.413 s / 810,392 KiB / 0; Charon 73.453 s / 1,115,932 KiB / 0; Aeneas 9.287 s / 332,288 KiB / 0. The receipts include cgroup peak and memory-event counters. Before each stage, the runner recorded the active scope maxima, the 24 GiB external reservation and 6 GiB pipeline reservation; the projected total stayed below the 50 GiB policy limit. Cargo reused the warm target cache at the recorded NUC path; that cache is intentionally excluded from this bundle.

After Charon, the untouched `Terminal.llbc` was copied to `Terminal-name-adapt.llbc` with a deterministic single-metadata rename for the unique `field::M31` constructor: function id 224, `item_meta.attr_info.rename`, `null` to `M31_constructor`. `name-adapter.json` records a deep reverse-transform check showing that no other LLBC JSON value changed. Both LLBC artifacts are retained with their hashes.

## Generated-output audit

Aeneas emitted the selected wrapper and the production `Public::terminal_qm31`, `terminal_parts`, and `composition_parts` as local, transparent, structured definitions. The field types M31, CM31, QM31, and PreparedQm31Multiplier are local and transparent. The LLBC has 531 function slots, 336 non-null function entries and 122 type declarations; 242 entries are local + transparent + structured, while 94 entries are opaque or nonlocal. A non-null `body` field alone is not evidence of transparency.

The generated translation metadata reports 220 functions, 59 types, and 60 trait implementations. `FunsExternal_Template.lean` contains 17 axioms. Compared with G's 20, the only removed entries are `core.array.from_fn`, `core.array.iter.IntoIter...next`, and `...next_back`; no external-template axiom was added. Other external templates remain. The complete list and generated file hashes are in `output/output-audit.json`.

The reproducible declaration-body comparison in `compare-generated-blocks.py` matches by Rust source file and item name, ignoring shifted source line spans. It reports 58/58 `Types.lean` declaration bodies byte-identical; in `Funs.lean`, 204 common declaration bodies byte-identical, 34 changed common blocks, 2 candidate-only helper blocks, and no removed declaration blocks. The changed blocks are listed by source/item and old/new body hashes in `generated-block-comparison.json`. These are textual output comparisons only and do not prove the replacement helper's semantics.

There was no Lean compilation, runtime replay, benchmark, CU measurement, SBF build, source adoption, or production acceptance decision in this experiment. Earlier failed translation attempts remain in the sibling F/G bundles; they are not overwritten here.
