# Cost-reuse inventory (2026-10-15)

> Note (2026-10-19): the R1 proof format is now the compact binary-multiproof format, fixed length 57,607 bytes (`evidence/format-adopt-20261019/REPORT.md`); 124,343 bytes below is the retired eight-way format.

This is a bounded inventory of already measured code paths that could inform future cost work. It does not recommend a protocol change or establish a portable CU reduction.

## Closest implementation lead: V8 terminal query weights

The V8 terminal optimization has the clearest source-level reuse opportunity: share four terminal query-weight calculations, specialize the fixed four-entry `LineM31Batch` shape, and fuse the carried image coefficient into the existing four-product terminal dot. The documented path keeps the same 22 query indices, all checks, deferred halvings, three earlier query-side dual folds, and malformed-input rejection order. It therefore provides a concrete implementation pattern to inspect if a later change targets terminal arithmetic.

The exact source files are [terminal_query.rs](../v8-no-work-100-20260907/experiments/terminal_query.rs) (SHA-256 `f51699776c77d2fc9e0fc9dfdd08ed9530b82230a068bdcedf919aefe240ee82`) and [query_arithmetic.rs](../v8-no-work-100-20260907/experiments/query_arithmetic.rs) (SHA-256 `57590907abf1c6a278cca0babc49b4c916a87a0a44e1f265b9bea28cc9fd52b1`). The arithmetic is called from [performance_verifier.rs](../v8-no-work-100-20260907/experiments/performance_verifier.rs) (SHA-256 `bf8a24c42c0d5493d2259fa19a70b1a8bf4ba168f661b71cfed6d33c70eebfbc`). The detailed implementation review is [terminal-query-review.md](../v8-no-work-100-20260907/terminal-query-review.md) (SHA-256 `2c96b1352f99f3a187ec5a9ba33a0db73052d1ad7688660edac967404bf94a40`); the per-variant measurement ledger is [terminal-query-results.json](../v8-no-work-100-20260907/terminal-query-results.json) (SHA-256 `b33fa3be0c97868960f0f14e8ee39a7c4822856a3e3eefd2cf2dbe5917e0f490`). That ledger selects the terminal-stack ELF `3d07a23833bac533f791b7ce2d619f4cd40aff6e1b5314c3b43be596b38c15a3`, measured in complete Pool + verifier + Registry + Token transactions. Its worst reported shape was withdrawal rollover at 1,047,041 CU with a 40,282-byte body; the selected build's maximum measured transaction remained 152,959 CU below its 1.2M transaction limit.

The measured sequence on the same V8 proof fixtures moved from 1,057,043 CU (shared-gamma predecessor) to 1,049,464 (`weight_prefix::<4>`), 1,047,204 (fixed four-entry specialization), 1,046,999 (fused image coefficient), and 1,047,041 CU (selected `inline(never)` layout used to clear a compiler frame diagnostic). The last adjustment costs 42–43 CU against the prior experimental variant. These are V8-to-V8 measurements, not a measured port to the current R1/P3 verifier.

For scale only, current h2 P3's matching 13-pair full-OS fixture has two transactions totaling 2,683,699 CU (stage 1: 1,390,128; terminal: 1,293,571), per [WIDE-PARSER-COSTS.md](WIDE-PARSER-COSTS.md), SHA-256 `09a536b1de5d1f8034745fe06c357820ad4b1fddc50b99931cf67e1fa0b1c45a`. Comparing V8's 1,047,041 maximum to that two-transaction sum gives about 61.0% lower arithmetic, but it is not a matched comparison: V8 is a one-transaction, 40,282-byte-body profile with a 1.2M cap; P3 is a two-transaction, 124,343-byte proof profile with separate stage-1 and terminal work and a 1.4M per-program cap. Their ELF, pool/source revision, transaction layout, account/settlement path, fixtures and proof hashes differ. The V8 maximum-proof hash `d3ad6c542317812487f9e2b1740f8db5bdbc96cb831a81273f3a7e47b0e01c8e` is not the reused P3 proof. The ratio is arithmetic context only and must not be reported as a portable 61% saving.

## Reuse boundary and open profile gaps

The terminal specialization is a code-reuse lead, not a proof that its fixed-shape conditions hold in the current implementation or that the resulting source is equivalent. Its accompanying Lean endpoint establishes source-shaped algebraic identities; the V8 review explicitly distinguishes these from a translated Rust/LLVM/SBF theorem. The V8 measurement record also leaves `global_security_certificate` and `universal_cu_bound` null, gives zero grinding-credit bits, and lists global accepted-recovery failure, full-view zero knowledge, resource-bounded Fiat–Shamir, and translated-source acceptance equivalence as unresolved. See the pinned `complete-performance-results.json` above and [complete-performance-review.md](../v8-no-work-100-20260907/complete-performance-review.md), SHA-256 `7bd3b2fa73db7815a7c2e2430603dfff94e966b2af7f1a9e833b1e91a3a6fb75`.

The inspected records do not supply a matched current-P3 implementation with a changed query count, a smaller fold schedule, or a ≥15% complete-transaction reduction. They also do not establish a universal CU cap for all accepted current-protocol inputs. Any reuse would need its own exact source/ELF pins, same-profile fixtures and complete transaction measurements, while retaining the current raw-security and source-correspondence obligations. This note makes no security or adoption decision.
