# Literal semantic context and prefix reuse

This inventory records existing list-level interfaces for constructing the semantic view from a literal transcript prefix. It does not establish source correspondence, acceptance, or a security bound.

`LiteralTranscript.c1At` reads only element zero and accepts that entry only when its message is `.initial`. The reusable theorem `c1At_append` in [LiteralTranscript.lean](../lean/LiteralTranscript.lean) states `0 < rs.length → c1At (rs ++ tail) = c1At rs`. Thus an already nonempty prefix keeps its C1 value when extended. The expression `c1At ((rs.take i) ++ [(rs[i].1,c)]) = c1At rs` holds for every `i < rs.length`, including `i=0`: `c1At` observes only the first message, while the challenge component is ignored. The current source has `c1At_append` for nonempty-prefix extension; the new `LiteralC1Prefix.c1At_take_current` draft combines that lemma with the indexed prefix decomposition for positive `i` and a direct zero-index case.

For the strict semantic parser, `LiteralSemanticPrefix.read_append` in [LiteralSemanticPrefix.lean](../lean/LiteralSemanticPrefix.lean) expresses the read of `xs ++ ys` as an `Option.bind` of the read of `xs` and the read of `ys` at the advanced offset. Its companion `read_length` shows a successful read has the same length as its input. The packaged [`LiteralSemanticTake.read_take`](../evidence/lean-literal-semantic-take-20261015/README.md) is stronger for prefixes: from `read eK offset xs = some out`, it proves for every `n` that `read eK offset (xs.take n) = some (out.take n)`. These results cover parser/list coherence, but do not by themselves construct the full `LiteralSemanticView` context or show a newly appended current message has a successful parsed view.

`LiteralSemanticView.read` in [LiteralSemanticView.lean](../lean/LiteralSemanticView.lean) is the existing context constructor for rounds `<25`: it parses the public statement, obtains C1 from `P.rounds ++ [current]` with an unused dummy challenge, strictly reads the prior semantic prefix, parses the current message, then calls `LiteralTypedContext.context` with the parsed public value and C1 word. Its `density` theorem handles a successful context by reusing `semantic_round_densityZ`; it does not provide a decomposition theorem for the successful `read` result. A mechanical bridge that exposes the parsed components of a successful `LiteralSemanticView.read`, analogous to `LiteralMatchingFacts.read_success_components`, remains a direct Option case analysis.

No-hit transport already has generic list lemmas: `GenericNoHit.hitFrom_append` splits the bad-event search across concatenated lists, and `GenericNoHitIndex.noHit_take` restricts a no-hit fact to a prefix; `not_bad_at_index` extracts exclusion at a particular row. The current consumer `LiteralOpeningGood.good_of_read_noHit` uses those facts with `LiteralMatchingFacts.read_success_components` and row-specific `LiteralOpeningBinding.*_bad_iff` theorems to rule out four opening challenge bad sets. This route is tied to the opening matching-data reader. I did not find an existing theorem that transports the `LiteralSemanticView.bad` event through a successful literal semantic context read and a matching prefix cut. `LiteralSemanticTake.read_take` establishes only successful parsing of the prefix and output prefix; an event-level semantic correspondence remains the missing interface.
