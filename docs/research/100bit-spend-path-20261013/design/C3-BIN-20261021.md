## Addendum (lead, 2026-10-20 night): hN is an adversary restriction — claim must be per query

Landed from `codex/cx-hn-starts-20261021` (`design/HN-STARTS-20261021.md`).
`recorded_more_than_33` proves that a fixed adversary querying 34 canonical
initialisation frames for unused public strings, then running any prover P,
has more than 33 recognised starts for every oracle, with acceptance
preserved. So `hN` (≤33 starts) is a restriction on the adversary, not a
protocol fact, and the earlier endpoint "deployedFailure < 2^-100 for
Q ≤ maxAdversaryQueries" was conditional on it. That endpoint must not be
cited without `hN`.

`R1FinalSoundnessBinFirstReadBudget.final_soundness` removes `hN` and derives
starts ≤ Q+1161 from R19, giving
`6(Q+1161)²/2^256 + (Q+1161)·15/2^109 + 2^-126 + 2^-454`. The per-start mass
15/2^109 ≈ 2^-105.09 is the real security parameter; the bound grows linearly
in the number of starts, as any Fiat–Shamir grinding bound does. The 1161
offset makes it exceed 2^-100 even at Q=0 (`replacement_not_100_bits`).

Lead ruling for the next step, pending the user's confirmation of the release
wording: the right form of "100-bit soundness" here is the query-normalised
one, ε(Q) ≤ (Q+1)·2^-100 over a stated query range, which is standard for
Fiat–Shamir arguments. Proving it needs the start count tied to the
adversary's own initialisation-frame queries plus a small constant for the
verifier's and compiler's reads, instead of the R19 total Q+1161. A job is
open for that. Release language must say "per oracle query", not "per attempt",
until the user rules otherwise.

erased schedule admission with the arbitrary-prover canonical reduction, R16
instance fields on admitted canonical runs, and composition of the typed
semantic, matching, checkpoint and backend checks. Two compiled
obstructions follow.

1. `D0ErasedWordObstruction.no_erased_final_reader`: the endpoint's decision
   `d : ErasedPrefix → ErasedMessage → Bool` is a pure function of the erased
   transcript, while the checked C1/C2/final words are filled in by the
   compiler from the whole oracle log. No erased d₀ can read them.
2. `D0OpeningRecoveryObstruction.depth18_counterexample`: with the zero
   oracle, two different packed leaves both open at one root. Recovering
   leaves from successful openings needs collision exclusion, and
   R13/R15-style premises stated for every H are stronger than needed.

Root cause: in `RawCutProverCompiler.verifier`, which is
`FS2.verifier … (decisionOnBytes d)`, the final decision cannot query the
oracle, so the verifier's Merkle path recomputation is not modelled as
hashing. It is carried by the source premises (R13, R15, R16, R3) instead.

Safe now: narrow each of those premises to non-collision runs. That is a
strict weakening, and the endpoint already charges κ for collisions.
Proposed, pending the user: generalise the decision to an oracle program
(`ErasedPrefix → ErasedMessage → Program Bytes State Bool`). A pure d embeds
with no queries, so existing results should become special cases, and the
verifier's own hash reads are already inside the 561 ≤ 1161 budget. A
feasibility study runs tonight; it changes no existing endpoint.

## Addendum (lead, 2026-10-21 00:50): domain separation is partial
