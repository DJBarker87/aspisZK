## Addendum (lead, 2026-10-20 night): hN is an adversary restriction — claim must be per query

Landed from `codex/cx-hn-starts-20261021` (`design/HN-STARTS-20261021.md`).
`recorded_more_than_33` proves that a fixed adversary querying 34 canonical
initialisation frames for unused public strings, then running any prover P,
has more than 33 recognised starts for every oracle, with acceptance
preserved. So `hN` (≤33 starts) is a restriction on the adversary, not a
protocol fact, and the earlier endpoint "deployedFailure < 2^-100 for
Q ≤ maxAdversaryQueries" was conditional on it. That endpoint must not be
cited without `hN`.

`R1FinalSoundnessBinFirstReadBudget.final_soundness` removes `hN` and derives
starts ≤ Q+1161 from R19, giving
`6(Q+1161)²/2^256 + (Q+1161)·15/2^109 + 2^-126 + 2^-454`. The per-start mass
15/2^109 ≈ 2^-105.09 is the real security parameter; the bound grows linearly
in the number of starts, as any Fiat–Shamir grinding bound does. The 1161
offset makes it exceed 2^-100 even at Q=0 (`replacement_not_100_bits`).

Lead ruling for the next step, pending the user's confirmation of the release
wording: the right form of "100-bit soundness" here is the query-normalised
one, ε(Q) ≤ (Q+1)·2^-100 over a stated query range, which is standard for
Fiat–Shamir arguments. Proving it needs the start count tied to the
adversary's own initialisation-frame queries plus a small constant for the
verifier's and compiler's reads, instead of the R19 total Q+1161. A job is
open for that. Release language must say "per oracle query", not "per attempt",
until the user rules otherwise.
