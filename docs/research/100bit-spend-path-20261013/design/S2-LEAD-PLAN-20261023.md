## Route A: contextual verification of actual SDK/std guard code

Keep the actual SDK `AccountInfo::try_borrow_data` / `try_borrow_mut_data`,
RefCell and compiler guard destructors in the verified context. First
replace the failed proof representation, not production source: isolate a
one-cell typed acquisition → Result move → shared deref → Drop context
with no raw output-array havoc. Show its returned guard has the same live
counter and original slice, including saturated shared-counter and
exclusive-borrow failure. Then check mutable acquisition/write/drop.
The mutable test must establish exactly the bytes written, not merely a
counter roundtrip. Use the actual supported foreign types or a verified
representation-preserving transfer; if Kani cannot express that transfer,
record that as the route's obstruction rather than using an opaque result.

After these gates, split by source prefix and live-guard context: CP borrow
and scan, public borrow and statement children, proof borrow and gate,
first child, copy, compiler cleanup. A contract is usable only after both
the actual callee check and its future caller/drop context pass. Ghosts
require byte-exact erasure and footprints. Typed tokens may organize the
proof but cannot replace the actual SDK bodies in route A. Compose the
small contexts with a symbolic heap/ownership invariant, not a giant
native/reference pair. Reuse the already checked copy/cleanup/geometry/order
results only after aligning their source pins, initial states and live
objects.

Estimated additional library work: 8–14 focused targets and 6–12
worker-days if typed contracts are expressible; feasibility is unresolved.
Common caller, history, backend and binary work above remains; a rough
S2 integration envelope is 20–40 worker-days with inherited child facts
available. This is planning uncertainty, not proof that work will finish
within that interval. The repeated full/one-byte formula-growth failures

## Route B: proposed named SDK borrow/guard trust item

Proposed name: `S2TrustedSdkBorrow` (not created). Pin the Solana SDK,
transitive account-info/std source, Rust/Kani/SBF toolchains, target and
features it interprets. v7 uses solana-program2.3.0 and
solana-account-info2.3.0 (lock checksum
`c8f5152a288ef1912300fc6efa6c2d1f9bb55d9398eb6c72326360b8063987da`).
The adopted production dependency closure must be checked independently;
the diagnostic lock is not automatically a release pin.

The versioned [SDK source](https://docs.rs/solana-account-info/2.3.0/src/solana_account_info/lib.rs.html)
defines the Rc/RefCell data carrier and maps the two data borrow operations
to RefCell calls with `AccountBorrowFailed` errors. Rust documents
[RefCell borrowing and guard lifetimes](https://doc.rust-lang.org/std/cell/struct.RefCell.html#method.try_borrow).
These public API semantics motivate B. Exact signed counters, saturation,
private layout and target pointer interpretation need the **pinned source**
contract, not an inference from current online API documentation (which
currently reports std1.99.1, unlike the retained Kani nightly).

Specify a primitive library transition system over an arbitrary heap map,
account data-cell identity, bytes and descriptor, signed counter and a set
of live linear guard tokens. Abstract cell/token identity is related to
the actual typed Rust carrier by this *explicit trusted* library relation;
it is never reconstructed from `usize` comparisons. Keep original arbitrary
metadata and aliases. A valid initial runtime heap and its relation to
AccountInfo is a separately supplied P6/runtime obligation. B does not
assume every hostile sequence of raw bytes is a valid Rust value.

For the currently scoped data-borrow path, the proposed complete field list
is the following. Each is universally quantified over related valid local
states and inputs, with no native adapter acceptance hypothesis.

| Proposed field | Exact library fact to trust, with call site/use |
|---|---|
| `account_data_cell` | `AccountInfo.data` dereferences to the SAME Rc-owned RefCell identity across borrowed handles; data and lamports cells remain distinct as established by runtime geometry. Used at stage1:957,961,970 and stage2:1007–1008. Does not assume that distinct account keys imply disjoint allocations. |
| `cell_payload` | That cell's payload is the original typed `&mut [u8]` descriptor (base, length, provenance) and its bytes in the heap, including empty slices. Relates both deref levels; no replacement buffer or synthesized zero bytes. |
| `cell_counter` | The abstract signed borrow state and live-token accounting denote the pinned RefCell's actual counter, not an arbitrary other Cell with equal integer address. Existing compatible external borrows are retained. Initial consistency and provenance must be proved/admitted by runtime P6, not invented here. |
| `shared_ok` | For 0≤n<isize::MAX, try_borrow_data succeeds, changes only that counter n→n+1 and returns a valid typed Ok Ref carrying a fresh shared token for that same cell and payload. Used at both shared-borrow sites in stage1 and stage2. |
| `shared_err` | For n<0 or n=MAX, shared acquisition returns exactly Err(AccountBorrowFailed), creates no token and leaves counter/payload unchanged. Saturation is taken from the pinned implementation, not omitted as unreachable. |
| `exclusive_ok` | For n=0, try_borrow_mut_data succeeds, changes only that counter to -1 and returns a valid typed Ok RefMut owning the same cell/payload. Used stage1:957. |
| `exclusive_err` | For n≠0, mutable acquisition returns exactly Err(AccountBorrowFailed), no token, no mutation. |
| `shared_deref` | Deref of the live Ref yields the cell's exact `&mut [u8]` value through a shared access, hence exact base/length/current contents through slice coercion, without permitting writes through the shared guard. Used scan-independent public/proof arguments and stage2 CP. |
| `exclusive_deref` | Deref/DerefMut of the live RefMut yields that same payload; writes made through its slice update exactly the corresponding payload positions. Does not assert that the caller writes the correct CP or performs a copy. Used stage1 CP scan and :985 copy destination. |
| `guard_move` | Moving a valid Ref/RefMut inside/outside a typed Result transfers the same token, cell and descriptor once, with no drop, extra borrow or byte changes; source is no longer an owner. Includes argument/return/local movement, not arbitrary byte reinitialization. |
| `shared_drop` | Dropping one live shared token with current n>0 subtracts one from the SAME counter and consumes that token, preserving payload. With intervening valid library operations, restoration follows from their ledger; it is not an unconditional claim of whole-scope initial=final. Used actual implicit destructors. |
| `exclusive_drop` | Dropping the unsplit exclusive token at -1 restores that SAME counter to0, consumes it and preserves its current payload including writes. No guard split/leak is present in these call sites; if discovered, extend the explicit method inventory and get a ruling. |
| `error_move_drop` | Moving/dropping Err(AccountBorrowFailed) creates/drops no guard and has no data/borrow effect; ordinary Result discrimination selects the corresponding typed arm. Does not specify caller error remapping. |
| `borrow_frame` | Each acquisition, failed acquisition, deref, move and guard Drop touches only its stated counter/token fields; no account keys/owner/flags/rent/lamports, Rc counts, other cell, bytes or oracle state change, except bytes explicitly written through an exclusive payload. This is a primitive library footprint, not the caller's final accountFrame. |
| `guard_liveness` | While the account Rc owner and a valid related guard context are live, the token's cell and payload remain allocated and usable with unchanged descriptor unless an expressly allowed library operation changes them. Does not authorize arbitrary realloc, free or concurrent/CPI mutation. |

These fifteen fields intentionally exclude `Ref::clone/map_split/leak`,
`RefMut::map_split/leak`, realloc, assign, Rc clone/free, lamport borrow,
CPI/reentrancy and concurrency; none is licensed by this narrow trust
proposal. If a reached scoped path uses one, inventory it and either prove
it or explicitly enlarge the proposed trust contract before use. Destruction
of account-owning Rc/Box/Vec values, their allocator effects, and ordinary
slice copying keep their existing S10/P6/std-copy qualifications and require
composition; `guard_liveness` does not cover them. In particular library
frame preservation is conditioned on legitimate operations, not on a free
assumption that the caller preserves memory.

**Conclusion-hiding audit:** no field mentions stage1/stage2 success, the
four child returns, candidate equality, fixed proof/public/CP bytes, accepted
observation, final output, oracle log, dV_frozen2 or S2CallerFacts. The
payload and counter identities are precisely the local library semantics
being newly trusted; they are visible additions to the trusted computing
base, not discharged proofs. Universal valid-state transitions and an
explicit live-token ownership ledger prevent choosing arbitrary True fields
or assuming a successful guard out of an invalid byte pattern. A small model
of these transitions should be constructed and checked for consistency,
including failed borrows and move/drop schedules; a model witness would show
satisfiability, not certify the SDK implementation. Caller cleanup order,
actual copy footprint, validation and runtime eligibility still must be
proved. Thus none of the proposed fields hides the enclosing conclusion.

On approval, implement an exact library specification and explicit trusted
interpretation record, exercise the caller against a spec implementation,
and extract/compose the caller proof in Lean using these fields. A stubbed
Kani run then proves **caller logic relative to B**, never actual SDK
internals. Prove a wrapper/source-erasure or per-call simulation linking the
unchanged caller to those specified calls; a new simplified adapter is not
substituted for the production caller without that proof. Keep the native
compiler's implicit cleanup sequence in the caller evidence. Link the final
conditional theorem to P6 and actual release carriers/ELFs.

Estimated B specification/consistency/interpretation work: 3–5 targets,
2–4 worker-days, then approximately 10–20 worker-days for common caller and
integration work with inherited cone results available. Cross-TX history,
backend and final binary binding may extend either route; B does not solve
them. Relative to A, B removes a recurring unsupported foreign-guard and
formula-growth obstruction, at the explicit cost of trusting these
particular SDK/std semantics. No protocol, security metric, collision budget
or source adoption is proposed.
