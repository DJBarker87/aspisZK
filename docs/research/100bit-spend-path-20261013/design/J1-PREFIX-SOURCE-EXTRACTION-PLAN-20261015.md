## Smallest extraction order

1. Extract `r1_wire::parse_record` alone first (source lines 39–74). Its direct Rust cone is `row_shape`, `Error::{InvalidRow,Length,Tag,NonCanonical}`, `LANES`, `CLAIMS`, `WideExact::from_le_bytes`, `WideExact::c1`, and `QM31::ZERO`. It also depends on slice length/index/range operations, `try_into().unwrap()` for the fixed 4-byte length field, `chunks_exact(32).enumerate()`, and `Result` propagation. `row_shape` is a small finite match; payload-size arithmetic is `0`, `32`, `28*32`, `(CLAIMS+LANES)*32`, or `LANES*32`.

   The smallest useful preflight is to isolate this exact declaration and its direct support declarations in one extraction probe, retaining both a message-free row and a row at/above 14. Do not reduce the probe to a hand-written fixed-row parser: that would not extract the actual branch or the canonicality loop. The successful field-parser imports already establish the relevant M31/CM31/QM31/Wide field-byte behavior, but their generated namespaces/types are separately retained; an extraction can reuse them only if the Rust/Aeneas type identities line up. No such connection is implied by matching names.

   Primary parser-specific translation risks are (a) the returned borrowed payload slice `&record[5..]`, (b) the fixed-size `try_into().unwrap()` conversion, and (c) the iterator loop over `chunks_exact`. Unlike the later serializer, this loop borrows an immutable input slice and does not mutate/reborrow a frontier vector. First see whether the exact cone translates without any source adaptation. If it does not, record the precise failing expression before considering any source change.

2. Add `ValidatedRecord` and `decode_k` next (lines 112–163). Its cone includes the private `{ row, framed }` token, `parse_record` as the issuance condition, row/offset checks, `checked_mul` / `checked_add`, `payload`, `.get(range)`, `chunks_exact`, and `QM31::from_le_bytes(&part[..16])`. The crucial separation is that `decode_k` itself only checks `row >= 14`; its assurance that each 32-byte value has zero high half comes from the token's construction through `Prefix::parse` calling `parse_record`. A source bridge should preserve that issuer/use relation, rather than prove `decode_k` in isolation and silently grant an unchecked token.

   Borrow risks are the token's borrowed framed slice and the nested ranges returned from it. Generic `const N` array construction and indexed mutation (`out[value] = ...`) are additional extraction points. A narrowly closed first probe should retain the actual method and token shape; if the Aeneas encoding cannot retain the lifetime relation, stop and report that boundary rather than replacing it with an unrelated decoder model.

3. Add `Prefix::parse` last (lines 268–292). Its direct cone is `Prefix<'a> { c1_root: &'a [u8;32], records: [&'a [u8];27] }`, `Error`, `row_shape`, and `parse_record`. It checks the initial 32-byte root, takes a fixed prefix, runs a 27-iteration row loop computing each exact framed size, stores borrowed subslices by row, advances an offset, and rejects any trailing bytes. `record` / `payload` / `validated_record` are consumers, not required to parse the prefix itself; include them only when proving the token-use bridge.

   The likely hard point is the loop updating a fixed array of borrowed slices while the loop's `framed` value borrows the input. Aeneas must preserve the common input lifetime across the array assignment. This differs from merely extracting a 27-element structural loop over owned values. The minimal preflight after steps 1–2 is an exact extraction of `Prefix::parse` with `row_shape` and `parse_record` as imported extracted declarations, then inspect translation shape before attempting any Lean theorem.
