## Meaning of deployed

Here `deployed` means the explicit R9 two-transaction oracle-program model:
tx1 either rejects or writes checkpoint bytes, Pool invokes its supplied nested
tx2 continuation with precisely those same bytes, and both transactions use
one memoized oracle. Acceptance is the resumed RunView verdict, and failure
means the binary recorded-public extractor returns `none` on that exact
RunView with independent private extractor coins. This defines a probability
without a free rational. It does not yet identify the supplied continuation
with the frozen Solana Pool/verifier caller: P2′ persistence alone and R20's
conditional field-copy agreement do not establish that identification.

## Why the existing R20 results cannot construct this caller law

The R20 `common_agreement`, `transfer_serialization_agreement` and
`withdrawal_serialization_agreement` theorems require `sameSnapshot` and
successful reconstruction and conclude a deterministic field/encoding
agreement. They do not mention the endpoint's arbitrary `d`, `P`, oracle
program, designated recorded log, or extractor. `ASQ8PoolHandoff.handoff_bytes`
likewise preserves request bytes across the extracted strip/normalization;
it does not prove the nested verifier executes `verifier D d` on a tx1-bound
public statement. Importing these theorems cannot prove an execution law
about identifiers absent from their conclusions. Their own R20 note leaves
this source/runtime provenance premise explicit. The cited commits
`f5d4b85a8` and `8138bc818` are gap-map addenda, not unconditional source
refinement theorems.

The available narrowing is exactly (verbatim):

```lean
def CallerReachability (tx1 : Tx1) (poolTx2 : PoolTx2)
    (D : LiteralByteProtocol.Decoder)
    (d : ErasedPrefix → ErasedMessage → Bool) (P : Prover) : Prop :=
  ∀ H run, (eval H (deployed tx1 poolTx2)).2.resumed = some run →
    run.2.2 = true → run = eval H (recorded D d P)
```

This is a full accepted-execution correspondence requirement. It is NOT
merely instruction ordering or account ownership beyond P2′, and it is NOT
a strictly weaker replacement for the old probability inequality. The proof
above establishes `CallerReachability → DeployedTransport`, not its reverse.
Consequently substituting it for `h_R9_transport` would violate the requested
signature criterion. No such substitution is advertised as a premise removal.
The concurrent d₀ construction can fix the model decision; the remaining
source/caller join must then bind the actual checkpoint, Pool statement,
ordered core log and nested verifier to that instance.

## Stage 2: checked persistence-only obstruction

`R9DeployedPersistenceObstruction.lean` supplies constant tx1 and Pool/tx2
programs. Tx1 writes `[]` and tx2 receives precisely `[]`. The continuation
returns an accepting RunView with empty public bytes; the actual binary
extractor's public parser fails, for every private coin tape. Its failure
probability is therefore exactly 1. For every decoder D and prover P, the
headline experiment with `d := fun _ _ => false` rejects for every oracle,
so its failure probability is exactly 0. The existing scan bound is strictly
less than 1. Thus `no_transport_from_persistence` proves the negation of
`DeployedTransport` for this persisted two-transaction model, and
`no_caller_from_persistence` proves the caller law is unavailable there.

This is a counterexample to deriving caller/refinement/transport from
same-bytes persistence alone. It is **not** an attack against the frozen
Pool, a model satisfying the frozen caller's missing execution relation,
or a counterexample to the intended theorem once that relation is supplied.
The all-false `d` exposes why a source verifier cannot be silently identified
with the endpoint's arbitrary decision. The counterexample does not use,
alter, or assume away any S-cone, M10, ownership or runtime implementation.
