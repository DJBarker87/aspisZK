## Critical distinction

A matching stored-bump derivation alone does **not** establish canonicality.
The existing native test `noncanonical_pda_with_matching_stored_bump_is_premise_bound`
(`programs/aspis-pool/src/pair_forest.rs:3937`) deliberately accepts a forged
Pool-owned noncanonical lane image. The analogous checkpoint/page test starts
at line 3971. Thus option (2) in the task proves derivation consistency but
needs account provenance to imply canonical account identity. It cannot, by
itself, prove that an attacker cannot select a different matching PDA.

## Provenance preservation argument

The induction is over successful transactions executing the frozen programs,
not over arbitrary host-created `AccountInfo` values.

1. AS8I obtains master/lane key-and-bump pairs from `find_program_address`,
   checks each passed key with `plan_fresh_program_pda`, freezes the output
   images before CPIs, and writes only after owner/size/zero/rent checks.
   The stored bytes come from those search results, not instruction bytes.
   Existing initialized images cannot pass the fresh zero-image gate.
2. AS8C obtains the checkpoint pair from the same search and passes that
   bump to the pure checkpoint planner and encoder. Its master update uses
   `..*master`, changing only checkpoint chronology. No checkpoint mutation
   instruction exists. AS8D and ASQ8 write a lane copied from the authenticated
   lane with exactly its old master/lane ID/bump. The direct lane encoder
   likewise writes `output[72] = lane.bump`.
3. All page creation/signing in the forest deposit path uses searched bumps;
   terminal hints only authenticate **already Pool-owned** pages. The terminal
   never allocates or assigns a root page using an untrusted hint. Legacy
   root-page creation likewise searches first (`processor.rs:807–831`,
   `929–933`, `1088–1092`, `1123–1148`). Legacy handlers require their own
   exact account formats and identities; they cannot reinterpret forest
   master/lane/checkpoint images as mutable legacy state. Distinct domain
   seed prefixes and fixed-width suffixes separate their signing families.
4. Registry initialize/schedule (both versions) search before storing. V2
   deployment authentication searches the loader ProgramData address and
   verifies the executable's loader-state pointer and passed ProgramData key.
   Subsequent registry loads re-search and compare canonical bumps. Pause,
   activate, retire and freeze (`Registry:787–908`, `1082–1203`) preserve
   bump fields through record updates. `incremented_registry{,_v2}` changes
   only generation. Freeze also changes flags/authority, not seed identity or
   stored bumps. Entry activation/retirement changes status/timing only.
   Neither the Pool nor R1 writes Registry-owned data.
5. Vault creation signs at the canonical vault-token PDA and initializes the
   SPL account with the canonical authority; the alternative initialized-vault
   branch checks the same authority. Subsequent deposit/withdrawal CPIs are
   TransferChecked only. No SetAuthority, Approve or CloseAccount path exists
   in these Pool custody helpers. Authority changes by an outside transaction
   require the off-curve Pool authority to sign. Hence a matching alternate
   authority hint cannot replace the canonical SPL authority.
6. At every use, the passed owner/metadata are checked before accepting the
   derived address. A successful one-shot derivation must equal the passed key
   (or the authenticated ProgramData field). An invalid/on-curve derivation
   returns an error. Zero sentinels are checked for unused hint fields.
7. B1 has no bump to preserve: the planner derives
   `create_with_seed(authenticated master, packed seed, Pool ID)`, compares
   it to the passed marker key and rejects a master/marker alias before any
   classification or creation. CPI uses that same plan's seed; account keys
   cannot change during execution. Reclassification checks post-CPI ownership,
   size, zero data and rent before the marker image is persisted.

This argument uses existing boundaries, explicitly: P2 for exclusive owner
writes, transaction rollback/persistence and immutable account keys; P3 for
SDK highest-valid-bump search, off-curve PDA derivation, invoke_signed, System
create/allocate/assign-with-seed semantics; P4 for the observed
metadata; P1 for ruling out a seed/address collision that would alias signing
families or an independently seeded account to the protected PDA.
The vault argument additionally needs the legacy SPL Token authority contract
quoted in the disposition below; that is an external token-program fact, not
a new theorem about the SVM. These are not newly verified runtime or
cryptographic facts. The claim always concerns the
pinned program code, as required by P7/R21.

## Mechanized property and scope

`P5BumpsCanonicalHistoryCx.lean` formalizes the induction: canonical creation
and identity-preserving updates imply every retained image is canonical;
accepted hints for such images resolve to the canonical key. It separately
proves marker derive-and-compare correctness and gives a counterexample to
canonicality from a matching derivation alone. Every theorem has `#print
axioms`; the final successful attempt checks five theorems and uses only
`propext` or no axioms.

`tools/p5-bumps-kit/prepare.py --check` binds the isolated Kani crate to exact
frozen source declarations, guard slices, initializer record literals, wire
assignments, and constants. No shipped file is instrumented. The type context
is deliberately reduced: parser/state validity and unrelated payload fields
are abstracted; raw field payloads use U32 arrays. These are component proofs,
not a Charon/Aeneas extraction or a whole-program SVM refinement.

The SDK stub is a symbolic **memoised** function keyed by program ID and the
complete, length-delimited seed tuple. It permits failure and arbitrary
addresses; it assumes neither injectivity nor bump canonicality for
`create_program_address`. Each guard slice has at most one distinct query;
a second distinct query is an explicit assertion failure, not a fresh
unconstrained response. Canonical-search helpers use a separate SDK contract:
a symbolic returned key/bump, with 1 ≤ bump ≤ 255. Highest-valid-bump semantics
are P3, not proved by the stub. Canonical existence is assumed only in search
helper harnesses. Symbolic account metadata and parsed scalar fields are
unrestricted except memory validity; the fresh-account observational shim
uses buffers of at most 16 bytes, so its address/metadata result is a component
control-flow check, not a test of full-size Pool account initialization.

The guard harnesses prove `success → derived address = passed account key`
and the exact seed tuple/program ID sent to derivation, with no precondition
that the account is canonical. ProgramData harnesses instead compare the
certificate's ProgramData field. Separate initializer-component harnesses
connect searched bumps to record fields and the source's exact stored byte;
state-update harnesses check bump and identity preservation. The complete
transaction/codec/runtime composition is the source argument above, not a
machine-checked refinement hidden in the stub.
