# Split-10 transaction cost comparison

This note reconciles the retained local LiteSVM evidence for the isolated
split10 candidate against the earlier split11 measurements. It reports whole
transaction totals and verifier/Pool log totals separately. The results are
measurements of the cost-probe path and do not establish protocol correctness
or security. The exact candidate has since been [adopted](evidence/split10-adoption-20261015/README.md).

The split10 adapter changes the first transaction from `[3, 11]` to `[3, 10]`
and carries the next query into the second transaction. The second transaction
then uses queries 10 through 21. Both transactions together still execute 22
query pairs. In the old split11 trace, tx1 logs queries 0 through 10 and tx2
logs 11 through 21.

## 13-pair transfer phase-log reconciliation

The transaction totals above can be checked against the nested program log
totals in the two retained run artifacts:

| Phase | Old split11 | New split10 | Difference |
|---|---:|---:|---:|
| Tx1 verifier CPI | 1,391,880 | 1,342,356 | −49,524 |
| Tx1 total | 1,392,386 | 1,342,862 | −49,524 |
| Tx2 verifier CPI | 1,184,073 | 1,233,599 | +49,526 |
| Tx2 Pool program total | 1,236,073 | 1,285,599 | +49,526 |
| Tx2 total | 1,236,579 | 1,286,105 | +49,526 |

The stage1 program log reports queries `0..10` in old split11 and `0..9` in
split10. The terminal log reports `11..21` in old split11 and `10..21` in
split10. Each tx1 total is 506 CU above its verifier CPI total; each tx2 total
is 506 CU above the logged Pool total. Thus the phase logs account for the
measured transaction totals. The small +2 CU combined-total difference is
visible across each split10 fixture; this note does not attribute that delta
to a particular instruction.

## Split11 compatibility run

The new ELF was also run through the unchanged historical gate driver with a
`[3, 11]` first-stage instruction. It accepted the 13-pair transfer at
1,392,390 / 1,236,579 tx1/tx2 CU and 295 / 879 bytes, matching the old tx2 and
measuring +4 CU on tx1 against the earlier split11 ELF. Its trace retains the
11+11 query split. This is a compatibility measurement, not a claim that the
two ELF builds are identical.

## Lifecycle and replay checks

The split10 13-pair success evidence includes an `unsealed-stage1` negative
check: the instruction was invoked, rejected with
`InstructionError(3, InvalidAccountData)`, and rolled back. It used 1,165 CU
and 295 serialized bytes. A separate replay scenario returned
`InstructionError(3, Custom(1095966758))`; its evidence records
`replay_preserved_settled_state_byte_exact: true`. Transfer success also
records the expected lane, history and nullifier-marker settlement checks.
The four larger runs record rollover-page, lane, history and marker settlement
checks; withdrawals additionally record destination/vault amounts.

The checked raw JSON, transaction traces, source copies, binary hashes, tool
pins, resource receipts and retained-key path/mode inventory are in
[`evidence/split10-v152-20261015`](evidence/split10-v152-20261015/). No keys
are included there, and this report makes no adoption or security claim.
