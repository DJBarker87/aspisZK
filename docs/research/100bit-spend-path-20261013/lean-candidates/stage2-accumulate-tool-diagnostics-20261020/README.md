The excerpt shows the only merge event `(327,326)->328`. Before merging, abs327 (region5) contains PLeft input loan s@4 and a nested PLeft consumed projection s@13; abs326 (region102) is a PLeft loan projection for s@13. The merged abs328 contains the PLeft input, consumed projection, and returned loan. Right-branch projection removes both merge inputs; the target retains the frozen input s@4 but has no output abstraction, so the existing `None,None` replay case registers no map entry. An accidental uninstrumented duplicate invocation of this exact LLBC also occurred during trace-kit setup; it exited 2 at the same mismatch in 0.803 s (107,712 KiB RSS, swap 0, same 2 GiB/Swap0 scope). It adds no evidence and is not part of the canonical attempt set.

This candidate is rejected; it did not produce Lean output.

The structural diagnosis remains that the body-side PLeft abstraction contains both the input loan and the `Option::as_deref_mut` result loan/write-back continuation. The right-side loop fixed point retains the input state but has no body-only result abstraction. A valid repair needs an explicit projection/correspondence for that mutable output into the loop state, preserving the back callback. Ending region 102 alone does not permit dropping it. No mapping rule has been established, so the unchanged production translation remains open.

## Rejected borrowed-Option branch split

To test a source-level alternative without changing production, I moved the `Some`/`None` dispatch ahead of the row loop and duplicated the row-loop body by branch. The `Some` loop receives the existing `&mut BatchedWeights` directly; the `None` loop performs the direct accumulator update. Row order, per-row `push`/value update, trace calls, the post-loop `terms` increment, and subsequent `rhs`/`power`/`next` updates were kept in source order. This avoids `Option::as_deref_mut` syntactically inside the loop, but it still carries mutable borrowed state across the loop.

This candidate is rejected: Charon succeeded in 0.402 s (211,728 KiB RSS, swap 0) and Aeneas failed at the same `InterpBorrows.ml:2731` marker assertion in 0.603 s (100,848 KiB RSS, swap 0), using the unmodified combined-v3 Aeneas binary. Both phases had fresh admission at `MemoryHigh=512 MiB`, `MemoryMax=2 GiB`, `MemorySwapMax=0`. Source, LLBC hash, commands, receipts, stdout and time logs are under `owned-option-branch-v1/`. It provides no proof and is not proposed for adoption. A further source redesign would need to make the batch state genuinely owned across the loop and explicitly preserve caller writeback and failure behavior.

The full caller transfer of ownership and error/panic behavior were not adapted or proved, so this isolated candidate is diagnostic only. Evidence is under `owned-state-v1/`.
