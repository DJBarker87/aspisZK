# Target-dependent reached code and its treatment

**Material difference:** Pool `processor::process_instruction` invokes `require_transaction_level_invocation_v1(get_stack_height())` only under `#[cfg(target_os="solana")]` (frozen `programs/aspis-pool/src/processor.rs:2423`). Native host execution omits this rejection gate. The verifier TX1/TX2 native inventories do not cover the Pool processor. Host helper proofs cannot establish the deployed Pool entrypoint's whole behavior.

Scope: frozen `4bb3b3f51e16b4525f1d10336e2b0bcbbd775387`, the345-entry TX1 and242-entry TX2 static inventories, plus an explicit inspection of the separately deployed Pool entry/SDK boundary. The inventories deliberately stop at opaque leaves and are conservative source call inventories, not compiler-certified complete SDK/std/Pool lifecycle reachability. Therefore this is a complete listing of the identified target switches and named runtime interfaces in those cones, **not** a claim that all transitive platform implementations are proved covered. Unknown coverage is retained below.

Frozen project target/cast search is retained in [NCR_TARGET_SEARCH.txt](NCR_TARGET_SEARCH.txt); exact inventoried body checks in [NCR_BODY_SCAN.json](NCR_BODY_SCAN.json). No active `target_arch="bpf"`/`"sbf"`, target-pointer-width or target-endian branch was found in those project bodies. The actual release triple is `sbpf-solana-solana`; the precise built-in `target_arch` spelling was not freshly queried. Host receipts identify Linux x86_64. None of this equates their compiler semantics.

## Layout, unsafe code and inactive switches

Both host x86_64 and the deployed SBPF ABI use64-bit pointer carriers, but that alone does not identify layouts, alignment or pointer provenance. SDK entrypoint explicitly uses `BPF_ALIGN_OF_U128=8` for serialized input padding; native x86_64's u128 alignment can differ. Its unsafe typed loads, shared Rc/RefCell cells, duplicate-account reconstruction and borrowing are precisely the ABI/SDK admission boundary, not proved by a Kani account value fixture. Do not transfer a native struct-memory image as wire format without a layout proof. The checked release codecs instead explicitly encode/decode little-endian bytes.

`r1_semantic::claims:42` allocates uninitialized typed storage, writes three `[QM31;29]` values through casts, and calls `assume_init`. Its Rust text has no target branch; validity depends on same typed layout, all writes, early errors and ownership. LPn leaf qualifications and allocation/Drop trust still apply. A host native result is not an SBF heap-layout/cleanup proof. This audit adds no new unsafe-code correctness credit.

The field `r0-e4-reference`/`r0-hoist-reference` clauses use `not(target_os="solana")`; both audit features are disabled in release and ordinary native helper samples, so those bodies are **not active host/SBF mismatches**. Likewise off-chain trace writers, RootHistoryPage constructors/reference decode/encode, client bump-hint derivation, `r0-op-count` and `audit-eight-way` are not deployed-path implementations. `pool-v1-kernel` explicitly admits the Pool module on SBF; host module availability without that feature does not establish SBF reachability. All switch locations are retained rather than silently treating compiled host-only code as deployed coverage.
