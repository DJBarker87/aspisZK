# D500: generic formatting instance needs a guard or a faithful model

The concrete std/dependency closure remains **OPEN**. This is not a counterexample to op227 or the privacy endpoint. It is a counterexample candidate to an unconditional generic formatting instance; the final verification record identifies whether both its Lean and native checks passed.

The deployed Rust 1.94.1 numeric formatting path returns the writer's error. `format_error_native.rs` supplies a writer whose first `write_str` returns `Err`, formats `17usize`, and checks the returned `Err`. A second writer accepts the same value, returns `Ok`, and receives the bytes `17`. The negative control deliberately expects success from the rejecting writer and must fail. The exact deployed `fmt::write` and numeric-formatting source items and hashes are in `formatting-source-finding.json`.

The pinned `Aeneas.Std.core.fmt.num.imp.DisplayUsize.fmt` is the function `fun x fmt => .ok (.Ok (),fmt)`. Its `Formatter` and `Error` carriers are `Unit`. `PV_B3Q_FormatCounterexample.concrete_rejection` refutes the instance of the **existing** `PV_B3P_Link_std_dependency_closure14` whose source port returns the observed writer error and whose model is that pinned function. Only the returned Rust `Err`/`Ok` tags are needed for the discrepancy; the lost formatted bytes are an additional issue. No formatter axiom or new trust item may be used to prove this finding. The initial rejected draft accidentally resolved an unqualified formatter name and is excluded.

An actual source call-cone proof could exclude formatting if every panic/error formatting path is unreachable under the endpoint's existing guarded domain. That proof has not been supplied here. A failed generic formatting instance does not prove such a path executes in op227. Optimized absence alone is not an exclusion certificate. Alternatively, the relevant formatting model and its consumers need a faithful writer/error-state interpretation.
