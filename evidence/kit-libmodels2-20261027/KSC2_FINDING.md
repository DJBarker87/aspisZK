| `IterMut.fold` | Callback adds10 to each item and then accumulates it. Equal accumulators do not suffice. |

The `any`/`all`/`fold` refutations concern the **unrestricted mutable-callback
interpretation**, whose interface is already insufficient: `FnMut F T Bool`
or `FnMut F (B×T) B` has no output for updated T, and the implementation drops
the continuation returned by P7 next. The kernel probes use the corresponding
value-only callback erasure; native callbacks exercise the missing write-back.
These are not assertions that a mutating Rust closure has a faithful translation
into that deficient interface. A faithful unrestricted replacement needs an
explicit mutable-item ABI/channel (or re-extracted library body with that ABI);
it cannot be installed as a magic implementation of the current deficient type.
A restriction to read-only items would require
a separately stated reached-callback theorem, not a silent model repair.
No particular counterexample is claimed reachable in deployed Aspis.

The proposed repairs are private KSC2 definitions/prose. No kit replacement,
shipped Rust, candidate, runtime contract or adopted theorem was changed.
Mutable `collect` remains UNDETERMINED: real `Vec<&mut T>` retains aliases that
can mutate the backing array after collection, while the kit lacks a proved
alias/write-back interpretation for returned B and its original s.
