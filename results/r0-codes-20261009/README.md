# R-C: literal R0 codes, folds and chords

Implemented in `aspis_core::r0` on base `783aa3f97`; executable source and
independent KATs are committed in `72282abe9205d20eb89c36f3757f5fff9d00262e`.
The implementation follows [SPEC §§3–5](../../docs/research/v8-r0-rust-20261009/SPEC.md)
and [PLAN, Decisions after S1](../../docs/research/v8-r0-rust-20261009/PLAN.md).
It adds one export to `lib.rs`; the existing field and production verifier
implementations are unchanged.

The new code uses `no_std` plus `alloc`. `CodeField` is the M31-algebra field
boundary, implemented for F=M31, CM31, K=QM31 and E=WideExact. The same
formulas work over each; field names in generic APIs do not fix QM31 where
the Lean generic K is instantiated by E. Domain coordinates and matrix
entries are computed in F and embedded into the selected field. As elsewhere
in this crate, raw F/K representatives must be canonical; WideExact enforces
canonicality internally. There is no new field type or dependency.

There is no FFT/prover encoder. `exact_initial_encoder(q,i)` and
`exact_final_encoder(F,u)` are pointwise word evaluators, suitable for the
88 opened positions and OOD evaluations. Cost per evaluation is O(message
length), with a shared table of natural basis values. Full words need not be
allocated. Messages are arrays of 1024 or 256 **natural coefficients**.

## Public API and specification mapping

All paths below are relative to `aspis_core::r0`. Functions with operational
inverses return `Result<_, Error>`; zero denominators are never replaced by
filtered challenges. Checked index constructors reject out-of-range values
including `usize::MAX`. There are no production `panic!`, `assert!`,
`unwrap`, `expect`, or panicking inverse calls in this module tree. Matrix
allocations use `try_reserve_exact`, with `Error::Allocation` on failure.

M_512 plus its inverse occupy 2 MiB on the heap (M_256: 512 KiB).
Keep a `NaturalBasis` instance across operations. Construction uses optimized
base-field arithmetic. Matrix application skips zero coefficients, and
`quotient_weights` applies Mᵀ Aᵀ M⁻ᵀ rather than building a dense 1024² E
matrix. The same shifts and monomial truncation are retained. Chord methods
require the initial-size basis and return `WrongLength` for the final-size
basis. Caller-supplied field operations and callbacks have their documented
algebraic/non-panicking contracts.

## Independent KATs and tests

[generate_kats.py](generate_kats.py) is a standalone Python 3 standard-library
oracle; [kats.txt](kats.txt) is its committed output, consumed directly by the
Rust tests. It never invokes Rust or imports a Rust-generated table.

* E multiplication expands multivariate polynomials and reduces by i²=−1,
  u²=2+i, v²=u; inversion uses a^(p⁸−2).
* Natural polynomial columns use polynomial convolution and the stated D_b
  recurrence. Conversion uses leading-term subtraction. Both full forward
  and inverse matrices are hashed in row-major canonical LE-u32 order.
* Encoders use converted monomial polynomials and Horner evaluation; the
  domain oracle exponentiates using n(i), independently of Rust's slot signs.
* Quotient weights use individual multiplication columns, constructing
  truncated X*N_j and X²*N_j, independently of Rust's transposed-factor path.
* Dense eight-limb outputs pin initial/OOD values, folds, final evaluations,
  φ, secants, both interpolation branches, all 1024 chord coefficients, all
  1024 quotient weights, and both functionals. Challenges exercise E\K;
  sampled circle points are in K\F.

Reproduce from the repository root:

```sh
python3 results/r0-codes-20261009/generate_kats.py --check
cargo test --release --config profile.release.overflow-checks=true --locked --offline -p aspis-core --lib r0::tests -- --nocapture --test-threads=1
cargo check --release --config profile.release.overflow-checks=true --locked --offline -p aspis-core --lib --no-default-features
```

The recorded executions wrap these payloads in capped scopes. The six release
tests cover both M*M⁻¹ and M⁻¹*M entry-by-entry at both sizes; N_2≠X² and
N_3≠T_3; all 2²⁰ domain indices and permutation uniqueness; all 2¹⁸ line nodes;
nonzero L across all 2²⁰ points for two seeded random non-base K points; dense
KATs; generic F/CM31/K/E use; random full-support E fold commutation; α=0;
φ inversion; both interpolation branches; functional row construction;
transpose pairing including the highest off-image columns; monomial
truncation; and explicit invalid-index/length/denominator failures.

For the on-image test, choose a random full-degree E message q, compute its
two endpoint evaluations, and subtract the specified interpolant I. A
test-only polynomial long-division oracle constructs the quotient through

```text
s = ((a+bX)*p − c*(1−X²)*r) / ((a+bX)² − c²*(1−X²))
t = ((a+bX)*r − c*p)         / ((a+bX)² − c²*(1−X²))
```

where (p,r) is the monomial pair of q−I. Exact zero remainders, degree bounds,
e1=e2=0, and `chord_message(quotient)=q−I` are checked. This last coefficient
equality checks the entire encoded word. Pointwise division is also compared
at selected indices. The test runs for unequal x and for equal x/opposite y.
No off-image quotient decoder is exported.

## Ambiguities and boundaries

No unresolved ambiguity was found in the requested §§3–5 formulas after
applying the post-S1 decision. These explicit boundaries remain visible:

* §3: “Lean R16 leaves `π` and `piv` as parameters; R0 does not instantiate
  them.” PLAN resolves the encoder choice: “no R16 transport.” This module
  selects no pivot/permutation and applies no T.
* §4: “There is no quarter inside `citedDualFold`. V2 multiplies its dot
  product by quarter.” Accordingly the quarter is a separate API value.
* §5: “with `z0≠z1` and both outside the F-rational circle” is the stated
  hypothesis for L's no-domain-zero property. The generic secant formula
  does not invent a sampler or a base-membership policy. `Point` exposes the
  circle equation check; point-policy enforcement remains with the caller.
  Interpolation explicitly fails when delta is zero.
* §5: “All matrices in this display have width 512, so shifting out the top
  entries implements monomial truncation.” The off-image chord map and its
  transpose preserve this behavior exactly. No natural-coordinate truncation
  or division-based weight interpretation is substituted.

These are implementation/test results, not a Rust-to-Lean refinement proof.
No Lean sources changed, no `#print axioms`/manifest replay was run (not a
formal release), and no SBF build, CU measurement, or stack-limit validation
was performed. The direct generic routines use fixed-size message/polynomial
scratch arrays; they are a reference API, not a claimed SBF-optimized kernel.
